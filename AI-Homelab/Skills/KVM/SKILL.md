# PiKVM-family KVM operations over REST

## When to Use

- Connecting to or managing a PiKVM / GL.iNet GL-KVM / similar KVM-over-IP unit over its HTTP API.
- Mounting an ISO as virtual media to install an OS on the attached host.
- Sending keyboard/mouse input to, or reading the screen of, a machine behind a KVM.

## Overview

Operate PiKVM and derivative KVM-over-IP units (e.g. GL.iNet GL-KVM) via the HTTP API at `https://<kvm-ip>/api/` — auth, virtual-media ISO install, HID control, screen reading. Always `curl -k` (self-signed TLS) and HTTPS only.

The user's lab device runbook lives at `/home/ubuntu/kvm.md` (credentials, verified device facts, and phase-by-phase ISO-install commands for the GL-KVM at 192.168.8.201). Read it first for that device; this skill carries the general method.

Before hand-curling an ISO install, check the pre-built n8n automation stack — health/fetch/mount/boot/unmount/orchestrator workflows with webhook gates: `references/n8n-iso-automation.md`.

For unattended (autoinstall) installs — seed-delivery decision table and the ISO-repack recipe: `references/autoinstall-iso.md`.

## Procedure

1. **Stage the password once** into `/tmp/kvm_netrc` (chmod 600, netrc format) and reuse via `PASS=$(sed -n 's/^password //p' /tmp/kvm_netrc)` — a secret retyped verbatim across tool calls gets masked to `***` in outgoing input and later calls fail 401.
2. **Auth** — three verified methods, prefer headers for one-offs:
   - Headers on any request: `-H "X-KVMD-User: <user>" -H "X-KVMD-Passwd: <pass>"`
   - Session: `POST /api/auth/login` with **form fields** `user=`/`passwd=` (NOT JSON) → `auth_token` cookie; validate with `GET /api/auth/check`.
   - Basic auth `-u user:pass` also works.
3. **Health-check subsystems** before acting: `GET /api/info`, `/api/hid`, `/api/msd`, `/api/atx`.
4. **ISO to virtual media (MSD)** — let the KVM pull the ISO itself, never stage it on the agent host:
   - `POST /api/msd/write_remote?url=<urlencoded-official-iso-url>&image=<name>.iso&timeout=1800` — the `timeout` param is the KVM's own remote-request timeout (default 10 s, far too short for multi-GB ISOs); set it generously alongside curl `-m 1800`. Long-polling: never interrupt, an aborted request aborts the download. Authoritative progress is the JSON stream this request emits (`result.written` bytes vs `result.size`) — run it as a background process and read its output.
   - Mount: `POST /api/msd/set_params?image=<name>.iso&cdrom=1` then `POST /api/msd/set_connected?connected=1`; verify `drive.connected=true` via `GET /api/msd`.
   - Local file alternative: `POST /api/msd/write?image=<name>.iso --data-binary @file.iso`.
   - Read an image back out of MSD storage: `GET /api/msd/read?image=<name>.iso` streams the raw bytes (verified byte-exact) — the way to pull an ISO that already lives on the KVM down to the agent host for repacking.
   - Cleanup: `set_connected?connected=0` then `remove?image=<name>.iso`.
5. **HID to host**: `POST /api/hid/set_connected?connected=1` — keyboard/mouse show `online: false` until connected. Drive installer: `POST /api/hid/events/send_shortcut?keys=AltLeft,F2` (comma-separated key names from kvmd keymap.csv `web_name` column) and `send_key?key=<name>&state=1|0` for individual keys, `send_mouse_move`/`send_mouse_button` for absolute mouse. WARNING: `POST /api/hid/print?text=...` is a silent no-op on some firmware (GL-KVM kvmd 4.82: returns `{"ok":true}` but types nothing) — do not trust its response; verify text actually landed on screen, and if not, type per-character with `send_key` press+release pairs (~0.1 s apart), which is verified to work everywhere shortcuts work. Key names must be exact web names — arrows are `ArrowRight`/`ArrowLeft`/`ArrowUp`/`ArrowDown` (NOT `Right`), delete is `Delete`, letters are `KeyJ` style (unshifted = lowercase; uppercase needs shortcut `ShiftLeft,KeyJ`), digits are `Digit2`, space is `Space`, `/` is `Slash`, `-` is `Minus`, `.` is `Period`, `=` is `Equal`, `_` is shortcut `ShiftLeft,Minus` (there is NO `Underscore` name), and every shortcut item needs the full web name (`ControlLeft,KeyC`, not `ControlLeft,C`). An invalid name returns HTTP 400 or `ValidatorError` and sends nothing: never pipe send_shortcut output to /dev/null until a key name has proven itself, and when the screen doesn't react, suspect the key name before suspecting the link. If `hid/set_connected` returns ok but `connected` stays false and `keyboard.outputs.available` is empty, the USB device cable to the target is not physically linked — no API call fixes that; verify empirically by sending a keystroke that should visibly change the target screen, then snapshot-compare. FOCUS: keystrokes go to whatever the target's OS considers focused — a window the KVM itself just spawned on the target (e.g. Shift+F10 cmd during Windows OOBE) may NOT have keyboard focus; typed keys vanish silently. Click inside the new window (mouse) before typing, and screenshot the input line to confirm text landed before pressing Enter. LAYOUT: key names produce characters in the TARGET's active keyboard layout, not the US default — e.g. with en-GB active, `Backslash` types `#`. Avoid layout-dependent characters in typed commands (run `cd dir` + `prog` instead of `dir\prog`) and verify typed text on screen. MOUSE: REST `send_mouse_move` can be broken on modified firmware (every param shape → ValidatorError) while the active mouse output is absolute (`usb`) and silently ignores relative deltas — the working path is the web UI's WebSocket: find its path by grepping the web bundle (e.g. `wss://<kvm>/api/ws?auth_token=<token>`, token from the form-login endpoint), speak the firmware's JSON event protocol (GL-KVM: answer `ping` events with `{"event_type":"pong","event":{}}`; move = `{"event_type":"mouse_move","event":{"to":{"x":X,"y":Y}}}` with `X=round(px/width*65535)-32768` (same for Y); click = `{"event_type":"mouse_button","event":{"button":"left","state":true|false}}` — button must be the STRING, an int silently no-ops).
6. **Screen reading**: `GET /api/streamer/snapshot?save=1` returns the raw JPEG bytes directly (not JSON) — save to file and vision-analyze. The `ocr=1` query variant can 500 on modified firmware; don't build polling loops on it. Full-res console frames (1920×1080) can make vision_analyze time out repeatedly — downscale to ~960 px wide with PIL (`im.resize((960,540))`, quality≈80) before analyzing. At downscaled size the vision model confidently hallucinates text (wrong hostnames, invented lines), so for any value you will report or act on, crop the relevant region from the FULL-resolution frame, upscale ~1.2×, and read that crop. Coordinates derived from vision crop math can be ~20 px off — after every click, screenshot and verify the resulting STATE (selection highlight, page change) rather than trusting computed coordinates; calibrate empirically on first use. For small colored UI targets (link text, accent buttons) on Fluent/OOBE-style pages, locate them by colour-scanning the full-res frame with PIL (filter pixels near the accent RGB, cluster, take the bbox center) — far more reliable than vision-guessed coordinates. Windows Fluent comboboxes (OOBE security questions etc.) do NOT open on Enter when focused — click them; after ArrowDown×N+Enter selection, screenshot the closed combo to confirm the actual selected value (arrow count ≠ list position).
7. **Power**: check `GET /api/atx` first — many units ship ATX disabled (`enabled: false`); then power-on needs the physical button or Wake-on-LAN (modified firmware may expose `/api/wol/*`). Do not assume remote power exists. To REBOOT a running Linux target without ATX: `POST /api/hid/events/send_shortcut?keys=ControlLeft,AltLeft,Delete` — systemd reboots on the console (verified).
8. **Multi-port units** (e.g. GL.iNet Comet X 4-port): select the target with `POST /api/switch/set_active?port=<unit.port>` (param is `port`, float form like `1.1` — not `id`). In `GET /api/switch`, `video.links` and `usb_otg.links` are PHYSICAL cable detectors — HID and virtual media cannot reach a port whose `usb_otg.links` entry is false, regardless of any other call. Confirm the physical link before planning an install.
9. **Boot from virtual media**: the firmware POST/boot-menu window is only 1–3 s. Reboot the target (Ctrl+Alt+Del if the OS is up), then immediately burst `snapshot?save=1` JPEGs ~0.7 s apart to catch the POST text and its boot-key hint; send candidate keys (F11/F7/F12/Del) one at a time with a snapshot after each. Read the actual key off the POST text rather than guessing. If the machine gives no readable POST hint (quiet splash), spam the setup key (Del on AMI Aptio boards, e.g. ZimaBoard2) continuously from the instant the reboot is sent — it lands in BIOS setup reliably. WINDOWS CAVEAT: Windows installers show "Press any key to boot from CD/DVD" and time out silently back to the next boot option — spam Space from the instant the reboot is sent (Linux installers like subiquity have no such prompt). BIOS CAVEAT: removable-media boot entries (e.g. `UEFI: <kvm> Optical Drive`) can be dropped or de-prioritized when the virtual CD is disconnected — after swapping ISOs, re-enter BIOS and re-assert Boot Option #1 before expecting the new ISO to boot.
10. **Driving BIOS/UEFI setup over HID** (AMI Aptio recipe): navigate with single-key `send_shortcut` — `ArrowRight`/`ArrowLeft` switch tabs, `ArrowDown`/`ArrowUp` items, `Enter` opens a value popup, pick with `ArrowDown`+`Enter`, `F10` then `Enter` saves and exits. Set the virtual CD (shows as e.g. `UEFI: Glinet Optical Drive`) to Boot Option #1 under the Boot tab. Snapshot + vision-analyze after every keypress batch to confirm the screen moved before continuing — never blind-send a long key sequence. A BIOS boot-order change persists across reboots: disconnect the virtual CD (`set_connected?connected=0`) before the installer's final reboot or the target reboots straight back into the installer.

## Interaction rules (user preferences)

- Wiping a target disk is destructive and needs explicit user confirmation first (state what OS/data is on the machine, from a snapshot, and wait for a yes). The user confirms tersely ("yes, wipe it") — take that as full authorization and proceed without re-asking.
- On a stop request, immediately kill any running KVM background scripts (key-spam, snapshot loops) via process_manage, then report in this shape: what is done+verified / what was in flight when stopped / where the target machine physically is now / next steps to resume. The machine's current screen state matters more than the script's.

## Pitfalls

- Modified firmware (e.g. GL-KVM, kvmd 4.82) deviates from docs.pikvm.org: `GET /api/status` may not exist (use `/api/info`); `/api/msd/insert`/`eject` and Redfish `VirtualMedia/MSD` paths can 404 — mount via `set_params` + `set_connected` instead. Trust live probes over upstream docs.
- `/api/msd/*` and `/api/hid/*` take **query-string** params, not JSON bodies; JSON silently no-ops or 400s. `/api/auth/login` wants form fields, not JSON.
- Probe route existence on unknown builds by POSTing an empty body and reading the code: 400 (param error) = route exists, 404 = absent. Cheap way to map a modified API.
- During an active `write_remote`, `GET /api/msd` is a LAGGING indicator: `storage.downloading` can read `None` and the image's `size` stays at its initial placeholder while bytes stream at full speed. Never declare a download stalled from `GET /api/msd` alone — confirm against the `write_remote` stream before killing/retrying.
- kvmd can answer 403 Forbidden on every auth method with a VALID password (auth-service blip, device reboot). Re-test auth after a few minutes before concluding the password rotated or launching a credential hunt across Vaultwarden/n8n; a healthy API (401 unauthenticated, 200 on `/`) with 403 on authed calls points to transient auth state, not a changed secret.
- kvmd answers HTTP 200 with `{"ok": false}` for logical failures — e.g. `set_connected?connected=0` when the CD is already disconnected returns `MsdDisconnectedError` at HTTP 200. Automation must branch on the `ok` field and verify final state via `GET /api/msd`; never treat the POST reply's HTTP status as success, and treat already-in-state errors as success in idempotent mount/unmount steps.
- `send_shortcut` accepts a SINGLE key name (`keys=Delete`) and performs a full press+release in one call — use it (not two `send_key` calls) for boot-key spam loops, one request per second.
- `/api/msd/reset` wipes custom MSD params — harmless idle, destructive mid-install.
- kvmd separates malformed credentials from wrong ones: a username with invalid characters (e.g. a literal `{{user}}` fragment from a broken upstream credential) → HTTP 400 `ValidatorError` "not a valid username characters"; a well-formed but wrong user/passwd → 401 Unauthorized. A 400 from an automation caller means the stored credential value is corrupted, not that the password rotated.
- Redfish may answer at `/redfish/v1` root yet 404 on the subsystem paths; partial Redfish is normal, fall back to legacy `/api/*`.
- GL-KVM MSD `partition_connect` exposes only KVM-internal storage partitions (`path=/dev/...`), never MSD image files — a seed/CIDATA image cannot be presented as a virtual USB stick, so NoCloud-style seeding is impossible on this firmware (probed; don't re-probe). For unattended installs (Ubuntu autoinstall, cloud-init seeds), put the config at the root of a repacked ISO instead: `references/autoinstall-iso.md`.
- Stage multi-GB ISO extraction in a disk-backed directory and `df` it first — the agent host's `/tmp` is a small tmpfs (~2 GB) and a ~3 GB extracted ISO tree overflows it mid-build, killing long repacks with ENOSPC.
- Map modified-firmware endpoints by grepping the web UI bundle: fetch `/`, extract `assets/*.js` paths, then `grep -oE '/api/[a-zA-Z0-9_/]+' <bundle>` — firmware-only routes surface this way (e.g. `/api/system/otg_functions` gadget toggles, `/api/wol/*`). Faster than probing one guessed path at a time.
